### Два вида программ

На вопрос «Где деплоить?» здесь нет одного ответа, потому что репозиторий собирает два разных вида программ:

- **Планировщик** (`apps/web`) рендерит страницы на сервере, отвечает на запросы `/api/*`, пишет JSON-файлы при каждой
  правке и решает целочисленную программу с помощью WebAssembly-сборки HiGHS. Ему нужен процесс, который постоянно
  работает, и диск, на который можно писать.
- **Руководство, его federation remote и стенд компонентов** — это файлы: HTML, CSS, JavaScript, поисковый индекс. Им
  нужны CDN, CORS на файлах remote и разумная политика кэширования — и больше ничего.

Хостинг, бесплатный и идеальный для второго вида, может оказаться бесполезным для первого. Поэтому глава начинает с
того, чего требует код планировщика, и только потом смотрит на цены.

### Три вопроса к любому хостингу

**Может ли он выполнять серверный рендер?** TanStack Start собирает сервер в виде Nitro output:
`node .output/server/index.mjs` запускает HTTP-сервер, который рендерит страницы, выполняет серверные функции и
обслуживает `/api/*`. Обслуживать его может всё, что запускает процесс Node или один из пресетов деплоя Nitro.
Статический хостинг не может: туда подходит только пре-рендеренная или чисто клиентская сборка — поэтому это руководство
и пре-рендерится.

**Может ли он выполнять API?** API-маршруты планировщика на закреплённом коммите — это фиды календарей
(`ics.$calendarId`, `ics-zip`), OAuth для синхронизации календарей (`$provider.connect`, `$provider.callback`) и план
для инструментов и моделей (`plan`, `plan-guide`, `plan-schema`, `plan-update`). На VM или в контейнере это обычный код
внутри процесса. На serverless-платформе каждый запрос может получить новый короткоживущий экземпляр: для чтения это
нормально, а для «запиши этот файл и прочитай его при следующем запросе» — нет.

**Может ли он хранить файл?** Этот вопрос решает всё, и ответ на него — в одном файле.

### Что хранилище требует от хостинга

Каждая запись в планировщике по замыслу проходит через один файл `plan-data`: `packages/plan-data/src/store.ts` на
зафиксированном коммите, сегодня это адаптер `fs` в `packages/plan-data/src/fs/`. Прочитаем зафиксированный файл
глазами того, кто деплоит, а не того, кто разрабатывает:

```ts file=packages/plan-data/src/store.ts lines=29-134

```

<WalkStep lines="29-38" title="Где живут данные">

В клоне репозитория хранилище находит `packages/plan-data/data`, поднимаясь вверх от рабочей директории. В контейнере
клона нет, поэтому директорию задаёт `PLAN_DATA_DIR`: смонтируйте туда том, один раз скопируйте в него `plan.json` — и
код менять не придётся.

</WalkStep>

<WalkStep lines="40-48" title="Что оно пишет">

План и правки к нему, историю изменений, состояние синхронизации календарей и `local.json`, где лежат секреты (client
secret календарей, адрес фида занятого времени). На сервере всё это живёт на томе. Файл с секретами никогда не должен
попадать в образ.

</WalkStep>

<WalkStep lines="100-105" title="Встроенный запасной вариант">

Если файла плана нет, хранилище отдаёт план, вшитый в сборку. Хостинг вообще без директории данных всё равно показывает
план — тот `plan.json`, из которого была сделана сборка.

</WalkStep>

<WalkStep lines="117-123" title="Пишет, только где может">

Даже отдача фида календаря может что-то записать (версию каждого события). Здесь это защищено: там, где ничего записать
нельзя, фид отдаётся из того, что уже сохранено.

</WalkStep>

<WalkStep lines="125-134" title="Переключатель">

`canWrite()` решает, показывает ли планировщик элементы редактирования. Он возвращает false, если `PLAN_READONLY=1` или
если файл плана недоступен для записи. Модуль планировщика уже принимает `canEdit` как проп (глава
«<ChapterLink id="build-time-microfrontends" />»), так что деплой только для чтения — это конфигурация, а не форк.

</WalkStep>

</Walkthrough>

Значит, у планировщика два честных режима деплоя. **Личному** деплою нужен постоянный диск с правом записи. **Публичная
витрина** может работать только на чтение на чём угодно, что запускает Node, с `PLAN_READONLY=1`. То, что режим только
для чтения без изменений заработает на serverless-хостинге, — наше прочтение этого кода; в проекте это не пробовали.

### Нативная зависимость

HiGHS находит `highs.wasm` рядом со своим JavaScript-файлом через `import.meta.url`. Бандлер, который инлайнит или
перемещает загрузчик, это ломает, а трассировщик файлов Nitro не видит файл, найденный таким способом. Конфиг решает обе
проблемы:

`ssr.external` говорит Vite не бандлить `highs` в серверный код: он остаётся `import` пакета на диске, где его загрузчик
найдёт `.wasm` рядом с собой.

</WalkStep>

<WalkStep lines="22-23" title="Скопировать весь пакет в output">

`traceDeps: ['highs*']` заставляет Nitro скопировать пакет в `.output/server/node_modules` вместе с `.wasm`. Та же
строка помечает внешним и `@sentry/*`, хотя на закреплённом коммите Sentry в репозитории никто не импортирует. По нашему
прочтению, это остаток; вреда от него нет.

</WalkStep>

Хостингу, который не умеет читать файлы из собственного бандла деплоя (edge-воркер с виртуальной файловой системой),
понадобилось бы вместо этого импортировать HiGHS как WebAssembly-модуль: это изменение кода и одна из причин, почему
edge — самый дорогой вариант из перечисленных ниже.

### Решение

Самый дешёвый хостинг, на котором планировщик работает без изменений кода, — **Fly.io**: машина на 512 МБ и том на 1 ГБ
обходятся в $3,84 в месяц. Это укладывается в $5 ежемесячного использования, которые Fly даёт аккаунту с привязанной
картой, так что фактически выходит $0. **Railway Hobby** стоит $5 и выгоднее, когда нулевая настройка важнее этих $5
(это официальный хостинг-партнёр TanStack Start). VM в **Hetzner** за €5,99 + НДС — выбор ради полного контроля и
настоящего cron, но ОС, TLS, бэкапы и деплой тогда на вас.

Цена одной машины с одним томом — короткий простой при каждом деплое и отсутствие failover: том принадлежит одной
машине. При масштабировании до двух экземпляров у каждого была бы своя копия плана — ровно та ошибка, к которой
подталкивает файловое хранилище.

Планировщик **пока не задеплоен**. Это рекомендация исследования, а не зафиксированное решение проекта, и карточки
решений этой главы помечают его как предположение.

### Статическая половина: GitHub Pages

Руководство, remote и стенд задеплоены — из одного workflow. GitHub Pages выиграл по цене и по количеству возни: никаких
аккаунтов, кроме самого репозитория, и он уже отправляет `Access-Control-Allow-Origin: *`, без которого хост не может
сделать `import()` remote с другого origin (проверено вживую через `curl -I`).


Каждый pull request и каждый push в `main` или `develop` собирает и тестирует. Публикует только push в `main`.

<WalkStep lines="21-24" title="Сайт по вложенному пути">

Сайт проекта живёт по адресу `https://<owner>.github.io/<repo>/`, поэтому каждой абсолютной ссылке в статической сборке

</WalkStep>

<WalkStep lines="26-29" title="Полная история">

Главы читают фрагменты кода из git на тех коммитах, на которые ссылаются, поэтому с shallow clone сборка упала бы.

</WalkStep>

<WalkStep lines="36-48" title="Проверка перед публикацией">

Проверяются контракт и каждый файл, диапазон строк и коммит, на которые ссылаются главы; собираются руководство и

загружается в тестовый хост с Playwright.

</WalkStep>

<WalkStep lines="55-60" title="Один артефакт">

Pages отдаёт один сайт на репозиторий, поэтому стенд копируется в `stand/` рядом с руководством (remote уже лежит в
`remote/v1/`), и вся папка загружается один раз.

</WalkStep>

<WalkStep lines="62-74" title="Деплой с минимальными правами">

Только задание деплоя получает `pages: write` и `id-token: write` (Pages проверяет подлинность workflow через OIDC).
Задание сборки может только читать репозиторий.

</WalkStep>

### Жизнь с десятиминутным кэшем

Pages отдаёт `cache-control: max-age=600` для каждого файла и никому не даёт это изменить. Для сайта это неудобство; для
federation remote — реальный риск, потому что хост может совместить устаревшую точку входа со свежими чанками. Вместо
того чтобы бороться с заголовком, сборка делает фиксированные имена безвредными:

- у каждого чанка в имени уже есть хеш содержимого;
- точка входа remote тоже его получает (`remoteEntry-[hash].js`), поэтому манифест всегда указывает на ту точку входа,
  которая соответствует его чанкам;
- манифест — единственное фиксированное имя, которое запрашивает хост, и хост запрашивает его с query-параметром,
  который меняется при каждой загрузке.

Остаётся одно окно: страница, открытая до деплоя, которая загружает remote уже после него, может запросить чанки,
которые деплой заменил. Планировщик считает любую ошибку загрузки состоянием «руководство недоступно» и вместо этого
даёт ссылку на статический сайт. Если это когда-нибудь станет важно, чистое решение — файл `_headers` в Cloudflare
(`no-cache` для манифеста, `immutable` для файлов с хешем).

Загрузчик, который всё это делает, показан в главе «<ChapterLink id="module-federation" />».

### Что изменило бы решение

- **Больше одного пишущего** (второй человек, второе устройство, которые редактируют одновременно): файлов с
  last-write-wins становится недостаточно, и следующий шаг — база данных, которая заодно открывает дорогу
  serverless-хостингам.
- **Превью для каждого pull request** у руководства: статические ассеты Cloudflare Workers дают их за $0 ценой аккаунта
  и токена в CI.
- **Работа по расписанию** (периодическая синхронизация календарей, очистка корзины по таймеру): процесс, который
  постоянно работает, или cron платформы (Vercel Hobby запускает его раз в день).
